# Калькулятор эффекта инициатив — контекст проекта

Оценка инициатив банка/финтеха: сколько принесёт, стоит ли запускать. Типы инициатив:
коммуникация по своей базе, рекламная кампания ФРК 1–4, вывод продукта на полку, пилот или акция.

## Главные принципы — не нарушать

1. **Считаем инкремент против counterfactual, а не результат.** Вопрос не «сколько клиентов придёт»,
   а «сколько НЕ пришло бы без инициативы». Всё остальное — приписанная себе органика.
2. **Честность важнее красоты цифры.** Каждое допущение имеет грейд источника
   (A — свой факт из BI, B — свой аналог, C — рыночный бенчмарк, D — догадка).
   Индекс уверенности < 0,6 → вердикт не может быть «GO», только «сначала пилот».
3. **Никогда не выдавать одну цифру.** Всегда три сценария. Точечный прогноз здесь — ложная точность.
4. **Арифметика только движком.** Не считать в уме и не в тексте ответа: результат должен быть
   воспроизводим и пересчитываем при смене допущения.

## Архитектура

```
src/calc.py         — движок. Единственный источник истины по формулам.
src/build_xlsx.py   — генератор Excel-зеркала модели (docs/*.xlsx), собирается ПОД КЕЙС.
docs/*.xlsx         — две собранные книги: ФРК-кейс с лестницей и кейс с листом «Сегменты».
cases/*.json        — конфиги реальных кейсов, они же примеры формата.
tests/stress_test.py— инварианты, крайние случаи, монотонность.
tests/recalc.py     — пересчёт формул книги без Excel и LibreOffice (библиотека formulas).
.claude/skills/     — навык для диалогового режима (обёртка над тем же движком).
```

**Инвариант проекта: `src/calc.py` и `src/build_xlsx.py` считают ОДНО И ТО ЖЕ.**
Любое изменение формулы в движке обязано быть продублировано в Excel, и наоборот.
Сверка обязательна после каждой правки — см. «Как проверять».
Копия движка в `.claude/skills/.../scripts/calc.py` должна совпадать с `src/calc.py` побайтово.

## Возрастные сегменты

Инициатива считается для одного или нескольких сегментов: `kids` (0–13), `teens` (14–17),
`youth` (18–24). Задаются в `audience.segments`, у каждого своя ЦА, воронка и юнит-экономика.

**Правила банка по возрасту — это факт, а не допущение модели.** До 14 лет счёт и вклад открывает
третье лицо в офисе по свидетельству о рождении; с 6 лет — детская карта и копилки в детском
приложении; с 14 — вход в банковское приложение, копилки, накопительные продукты, брокерский счёт,
заказ карты, подписка Прайм, программа лояльности; с 18 — весь функционал банка и экосистемы.
Кодируется в `PRODUCT_AGE_GATE`; `meta.product` выбирает, какой порог применяется.

Сегменты сводятся в **один взвешенный прогон** (`resolve_segments`), а не в N отдельных:

- воронка (approval, activation) — вес по эффективной аудитории и по одобренным;
- экономика клиента (баланс, оборот, обслуживание, отток, ramp) — вес по числу клиентов;
- **ставки (NIM, CoR) — вес по балансу, интерчейндж и кэшбэк — по обороту.** Из-за этого
  `баланс_средн × NIM_средн` равен посегментной сумме **точно**, а не приблизительно.
  Не менять на «просто среднее по клиентам»: это сломает точность и тест это поймает.

Приблизительными остаются **отток и ramp-up** — у них нет мультипликативной базы. Если кривые
жизни сегментов расходятся сильно, считать их отдельными кейсами и складывать NPV.

Продукт, недоступный сегменту (брокерский счёт детям, кредит детям и подросткам), **исключает
сегмент из расчёта с явным сообщением**, а не молча обнуляет его вклад. Частичная доступность
(карта детям только с 6 лет) режет достижимую долю сегмента и тоже пишется в валидацию.

## Модель — конвейер

```
ЦА_эфф = Σ (Размер сегмента × Достижимая доля)
Показы = Бюджет / CPM × 1000
Охват канала = 1 − e^(−λ),  λ = Показы / Размер ЦА        (кривая Пуассона, потолок 98%)
Частота = λ / Охват                                        (эффективная 3–6)
Комбинированный охват = 1 − Π(1 − Охват_i)                 (допущение независимости каналов)

Заявки(perform, internal) = Показы × CTR × CR
Brand-uplift = Σ (uplift_i × Охват_i × МИН(1; Частота_i/3))
Заявки(brand) = Органика/мес × Uplift × (Месяцы кампании + Halo × Затухание)

Инкремент = Заявки × Approval × Activation × (1 − Каннибализация) × (1 − Deadweight)

Маржа/клиент/мес = (Баланс×NIM/12 + Оборот×Интерчейндж + Комиссии) × k_маржи
                   − (Оборот×Кэшбэк + Обслуживание + Баланс×CoR/12)
Активные_m = Активные_(m−1) × (1 − Отток) + Приток_m
NPV = Σ (Net_m / (1 + r_мес)^m),  r_мес = (1 + r_год)^(1/12) − 1
```

Три типа каналов: `internal` (свои каналы, задаётся абсолютный охват базы),
`perform` (прямой отклик, атрибутируется), `brand` (охватные — работают только через прирост органики).

Уровни ФРК вложены: **4 ⊂ 3 ⊂ 2 ⊂ 1**. Движок сам строит лестницу и считает предельную отдачу
каждого шага вверх. Это главный вопрос при выборе уровня — не средний ROMI, а `marginal_npv` шага.

## Что уже вскрыли тесты — не сломать обратно

Каждый пункт закрыт кодом. Если правите движок, проверьте, что защита осталась.

| Проблема | Где закрыто |
|---|---|
| Горизонт короче кампании → часть бюджета и притока молча теряется | `validate()` |
| ЦА = 0 → охват и brand-эффект обнуляются, прямые заявки остаются, результат правдоподобен и неверен | `validate()` |
| Охватные каналы при нулевой органике → весь бюджет даёт 0 заявок | `validate()` |
| Насыщение канала: доп. бюджет не даёт вообще ничего (охват 98%, частота выше 4,5) | `validate()` |
| Множитель конверсий применялся дважды (к CTR и к CR) — пессимистичный сценарий был 0,36 вместо 0,6 | `apply_scenario()`, `tornado()` |
| Выплаты за привлечение идут за ВСЕХ сработавших, а инкремент меньше — платим за deadweight | `acq_cost_per_client` в `run_pl()`, база — `_activated_raw` |
| Вердикт предполагал, что пессимистичный сценарий = худший. При отрицательной юнит-экономике это неверно | `main()`: min/max по сценариям + детектор инверсии |
| Доли сегментов округлялись в отчёте — Excel и движок расходились на сотни рублей NPV | `resolve_segments()`: доли и эффективная ЦА не округляются |
| Продукт, недоступный сегменту по возрасту, молча считался доступным | `PRODUCT_AGE_GATE`, `segment_availability()` |

**Инверсия сценариев** — важнейший диагностический сигнал: если оптимистичный NPV хуже базового,
маржа клиента ниже стоимости его привлечения. Никакой объём и никакой рост конверсии это не чинят,
менять надо экономику. Движок это ловит и пишет отдельным флагом.

## Правила предметной области

- **Каннибализация по умолчанию не ноль.** В банке новый продукт почти всегда ест старый.
- **Кредитные продукты без Cost of Risk не считать.** Без него кредитка всегда выглядит прекрасно.
- **Для акций всегда спрашивать deadweight.** «Скидка дала +40%» бессмысленно, если половина взяла бы и так.
- **Brand-эффект не атрибутируется по last-click.** Если в модели ТВ или наружка — явно писать,
  что цифра держится на допущении об uplift и требует geo-holdout или MMM.
- **Для `product_launch` главная цифра — NPV, а не ROMI.** ROMI считается только к маркетинговым
  затратам и не видит IT-разработку и opex: будет выглядеть отлично при глубоко отрицательном NPV.
- **Лестницу ФРК считать всегда**, даже если попросили конкретный уровень. «А нужен ли ТВ» —
  самый дорогой вопрос в брифе.
- **Для детей до 14 лет заявитель — родитель, а не ребёнок.** Медийная ЦА, конверсия в заявку
  и канал должны быть родительскими; push и in-app в банковском приложении до ребёнка не доходят.
- **Сегменты не смешивать в одну «среднюю» юнит-экономику вручную.** Баланс и оборот
  восьмилетнего и двадцатидвухлетнего несравнимы — взвешивание делает движок.

## Как запускать

```bash
make calc CASE=cases/frk1_debit_card.json   # расчёт одного кейса
make test                                    # стресс-тесты движка
make xlsx CASE=cases/<файл>.json             # пересобрать Excel под кейс
make check                                   # тесты + сверка Excel с движком по CASE
make check-all                               # сверка по всем кейсам разом
make sync                                    # синхронизировать копию движка в навыке
```

Без make: `python3 src/calc.py cases/<файл>.json`

## Как проверять

1. `make test` — инварианты и крайние случаи. Должно быть 0 провалов.
2. **Сверка Excel с движком обязательна после любой правки формул.** `make check-all` собирает
   книгу под каждый кейс, пересчитывает её (`tests/recalc.py`, библиотека `formulas` — ни Excel,
   ни LibreOffice не нужны) и сверяет NPV и инкремент по всем уровням ФРК и всем трём сценариям.
   Расхождение допускается до рубля.
3. Excel собирается **под конкретный кейс**, поэтому сверять надо каждый: один ловит лестницу ФРК,
   другой — выплаты за привлечение и инверсию сценариев, третий — взвешивание сегментов.
4. Зелёный recalc доказывает, что формулы *вычисляются*, а не что они *верны*. Ошибка в диапазоне
   даёт чистый файл с неправильными числами — сверяйте значения, а не только отсутствие `#REF!`.

## Стиль

Русский язык во всём: код, комментарии, вывод, документация. Числа — рубли, проценты долями.
Комментарии в коде объясняют *экономический смысл*, а не синтаксис.
