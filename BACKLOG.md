## P1 — Кривая насыщения канала

**Зачем.** Сейчас модель линейна: удвоение бюджета удваивает показы. В реальности после
некоторого порога растёт только цена. Есть только предупреждение в `validate()`, но расчёт
всё равно оптимистичен. На кейсе ФРК 1 удвоение бюджета дало ровно 0 дополнительных
brand-заявок — это правильно по охвату, но по перформансу модель всё ещё завышает.

**Что делать.** Ввести `saturation_budget` на канал (исторический бюджет, при котором
конверсии подтверждены) и функцию отдачи вида `эффективные_показы = S × ln(1 + Показы/S)`
или степенную `(Показы/S)^α, α ≈ 0.7–0.85`. Параметр вынести в конфиг, дефолт `α = 1` —
чтобы старые кейсы не поехали.

**Как проверить.** Добавить в `tests/stress_test.py` тест: при `α < 1` удвоение бюджета
даёт прирост клиентов строго меньше чем в 2 раза, но строго больше нуля.

## P1 — Кривая оттока вместо плоской

**Зачем.** Отток задан плоским процентом в месяц. Реальная кривая: высокий в первые 2–3 месяца,
дальше выполаживается. Плоский отток **завышает** LTV на длинном горизонте и занижает
на коротком. Это напрямую бьёт по LTV/CAC — метрике, на которой стоит вердикт.

**Что делать.** Кусочная функция: `churn_early` первые N месяцев, затем `churn_steady`.
Либо выживаемость Вейбулла, если найдутся данные на калибровку. Задавать на уровне сегмента —
именно здесь плоский отток врёт сильнее всего.

**Как проверить.** Прогнать `cases/frk1_debit_card.json` с обеими моделями и посмотреть,
меняет ли это вердикт по уровню ФРК. Если меняет — приоритет поднять до P0.

## P2 — Вирусная петля для реферальных программ

**Зачем.** Приглашённый клиент сам может стать реферером. Сейчас петли нет — модель считает
одну волну. При K-факторе выше 0,2 недоучёт становится заметным.

**Что делать.** Ввести `k_factor` и число волн: `итого = волна_1 × (1 + K + K² + …) = волна_1 / (1 − K)`
при K < 1. Обязательно жёсткое ограничение и явный флаг при K ≥ 0,5 — модель бесконечного
роста в реальности не работает.

## P2 — Калькулятор размера выборки для пилотов

**Зачем.** Для типа `pilot` в навыке есть формула `n ≈ 16·p·(1−p)/d²`, но её считает Claude,
а не движок. Значит она не воспроизводима и не покрыта тестами. Главный вывод по пилоту —
«хватит ли выборки, чтобы вообще что-то доказать» — должен считаться кодом.

**Что делать.** Функция `sample_size(p_baseline, mde, alpha=0.05, power=0.8)` в `calc.py`,
вывод в JSON рядом с `validation`. Плюс обратная задача: при заданном размере выборки —
какой минимальный эффект вообще детектируем.

## P3 — Калибровка бенчмарков на своих данных

**Зачем.** Дефолты в навыке — рыночные диапазоны, грейд C. Каждая замена на свой факт
поднимает грейд до A и напрямую двигает индекс уверенности, от которого зависит вердикт.

**Что делать.** Выгрузить из BI по закрытым кампаниям: фактические CPM, CTR, CR по каналам,
approval, activation, отток по когортам, средний баланс и оборот по продуктам.
Заменить таблицы бенчмарков в `SKILL.md` и дефолты в `cases/`.

**Коннекторы.** BigQuery, Amplitude, Pendo, Similarweb, Supermetrics — требуют авторизации
через настройки коннекторов на claude.ai. Приоритет: сначала BigQuery/DWH (воронка и
юнит-экономика), потом Supermetrics (факт по медиа).

## P3 — План-факт

**Зачем.** Модель предсказывает, но никогда не узнаёт, попала ли она. Без обратной связи
бенчмарки не улучшаются.

**Что делать.** Формат `cases/<имя>.actual.json` с фактическими результатами и отчёт
«план против факта» по каждому уровню воронки. Накопив 5–10 кампаний, пересчитать дефолты.
